# 模块重复比对与工程整合

日期：2026-06-11

## 结论

当前工程中有两批相近模块：

1. `research_agent/`：顶层正式自建科学把关包，适合承载长期主线。
2. `创新点和问题提出Agent/src/catalysis_question_agent/` 中的 `research_pipeline*`、`question_agent_adapter.py`、`protocol_registry.py`、`audit_gates.py`：上一轮为了快速打通 dry-run 增加的桥接层。

整合后采用以下分工：

```text
创新点和问题提出Agent
  只负责前端文献证据、共识/争议、问题卡片生成

research_agent
  作为自建科学把关主线，负责 P0/P1/P2... gate、protocol、schema、adapter

run_research_pipeline.py
  保留为兼容入口，但 P0 审计已经调用 research_agent
```

| P0 schema | `research_agent.schemas.core` | `catalysis_question_agent.research_pipeline_models` 的部分对象 | 顶层为准；旧 schema 只保留 P1 dry-run artifact |
| 计算可验证性 | `research_agent.gates.feasibility.ComputationalFeasibilityGatekeeper` | `catalysis_question_agent.audit_gates.question_preplanning_gates` 的 G2 逻辑 | 顶层为准 |
| Protocol Registry | `research_agent.protocols.registry.ProtocolRegistry` + `core_protocols.yaml` | `catalysis_question_agent.protocol_registry` + `protocols.yaml` | 顶层为准；顶层 registry 已兼容旧 YAML 字段 |

## 已完成的整合动作

- `catalysis_question_agent.research_pipeline.ResearchPipeline` 已改为调用：
  - `research_agent.adapters.question_agent_adapter.QuestionAgentAdapter`
  - `research_agent.gates.orchestrator.AuditGateOrchestrator`
  - `research_agent.protocols.registry.ProtocolRegistry`
- `research_agent.protocols.registry.ProtocolRegistry` 已兼容旧 YAML 字段：
  - `software` -> `supported_software`
  - `publication_text_template` -> `publication_boundary`
  - `reference_state_definition` -> `required_reference_states`
  - `audit_checks` -> `audit_rules`
- `run_research_pipeline.py` 现在会先输出：
  - `p0_audit_summaries.json`
  - `p0_audit_report.md`
  - `audit_gates.json`
  - `audit_gate_report.md`
- 如果 P0 为 `BLOCK`，不会继续生成结构、输入、AiiDA dry-run task 或计算 claim。

## 当前示范结果

命令：

```powershell
python "创新点和问题提出Agent\run_research_pipeline.py" `
  --question-output "创新点和问题提出Agent\outputs\debug_protocol_gate" `
  --output "pipeline_outputs\integrated_scaffold" `
  --max-questions 3 `
  --max-protocols-per-question 3
```

结果：

```text
Selected questions: 0
Structures: 0
Tasks: 0
Claims: 0
Gate summary: PASS 5 / WARN 17 / BLOCK 39
```

这是预期行为。原因是当前问题卡里要求的 `oxygen_vacancy_formation_protocol`、`neb_barrier_protocol`、`bader_charge_protocol`、`pdos_analysis_protocol` 等仍是 `planning_stub`，顶层 P0 的 G3 会阻断后续计算主线。

## 工程主线

后续新增自建模块时应优先放到：

```text
research_agent/
  schemas/
  adapters/
  gates/
  protocols/
  structures/
  inputs/
  aiida_bridge/
  results/
  figures/
  claims/
  manuscript/
  compliance/
```

`创新点和问题提出Agent/src/catalysis_question_agent/` 不再新增新的科学把关主模块，只保留：

- 前端文献/问题发现逻辑。
- 对 `research_agent` 的兼容调用入口。
- 历史 dry-run artifact 写出逻辑，直到 P1/P2 模块迁入顶层包。
