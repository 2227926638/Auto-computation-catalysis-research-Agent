# 创新点和问题提出 Agent 自动化升级方案

日期：2026-06-03

## 1. 升级目标

当前 Agent 已完成 MVP：可以从本地文献库抽取证据、生成共识/争议候选、产出问题卡片并评分。但是它仍然更像一次性手动运行器，缺少持续搜集、持续记忆和主动推送能力。

后续升级目标是把它改造成“领域情报闭环 Agent”：

1. 能持续盯住特定领域的优秀信源。
2. 能把新证据并入长期认识，而不是每次从零总结。
3. 能定期生成变化报告、风险提示和候选创新问题推送。

## 2. 总体架构

```text
优秀信源注册表
  -> 增量搜集 Harvester
  -> 来源质量/相关性初筛 SignalRanker
  -> EvidenceBuilder
  -> InsightLedger 长期认识账本
  -> QuestionGenerator / Reviewer
  -> DigestBuilder 自动推送
```

推荐保持“单个复合 Agent + 可审计模块”的路线，暂不拆成多个异步 Agent。原因是当前任务的关键瓶颈不是并发，而是证据质量、认识连续性和新颖性风险控制。

## 3. Phase 1：认知整合层

本阶段优先实现 `InsightLedger`，解决“单次运行结果不能积累”的问题。

### 3.1 核心对象

每条长期认识写入账本，拥有稳定 ID：

```text
claim_id
source_kind                 # consensus / controversy / question
topic
proposition                 # 命题或问题标题
supporting_evidence_ids     # 稳定证据键 EVK-*
opposing_evidence_ids       # 稳定反向/争议证据键 EVK-*
linked_question_ids
source_record_ids
controversy_status
novelty_implication
computability_implication
confidence
first_seen_run_id
last_seen_run_id
first_seen_at
last_updated_at
update_count
metadata
```

注意：原有 `EVD-0001` 是单次运行内编号，不能直接作为长期证据 ID。账本层会根据来源 DOI/URL/本地路径/题名和证据摘录生成稳定 `EVK-*` 键，避免每次重跑都误判为新增证据。

### 3.2 每次运行产生的变化报告

每次运行后，Agent 不只是重写共识列表，而是输出 delta：

- `new_claim`：首次进入账本的共识/争议。
- `strengthened`：新增支持证据，认识增强。
- `challenged`：新增反向或争议证据，认识边界需要复核。
- `new_question`：首次进入账本的问题卡。
- `unchanged`：再次观察到，但没有新的稳定证据键。

运行目录新增：

```text
insight/insight_ledger_snapshot.json
insight/insight_delta.json
insight/insight_delta_report.md
```

真实库配置中的长期账本位置：

```text
outputs/insight_ledger/real_ammonia_ru_ceo2_debug_ledger.json
```

### 3.3 当前已完成

已新增：

```text

```

已扩展：

```text

```

## 4. Phase 2：优秀信源搜集层

目标是让 Agent 具备特定领域信源搜集能力。

计划模块：

```text
source_registry.py
source_harvester.py
signal_ranker.py
```

信源分级：

- S 级：同行评议论文、综述、顶级会议 keynote、权威数据库。
- A 级：ChemRxiv/arXiv 预印本、基金项目公告、团队报告。
- B 级：高质量产业白皮书、优秀媒体深度报道、专家访谈。
- C 级：普通网页、新闻短讯，只作线索，不作结论证据。

第一批推荐接入：

- OpenAlex：开放论文检索和近年相似工作监控。
- Crossref：DOI 和出版元数据核验。
- Semantic Scholar：引用图谱、相似论文和推荐候选。
- arXiv/ChemRxiv：预印本线索。
- 本地合成氨文献库：正文级证据来源。

验收标准：

1. 给定领域关键词，可以自动生成 `new_sources.csv`。
2. 每条来源有质量等级、相关性分数和是否进入正文证据抽取的判定。
3. 不把 C 级来源升级为论文结论证据。

## 5. Phase 3：认识再思考与新颖性风险

目标是让 Agent 能围绕长期账本做二阶思考。

计划模块：

```text
insight_reflector.py
novelty_risk_reranker.py
question_evolver.py
```

核心能力：

- 从 `strengthened` 共识中寻找“已被大家知道但机制仍未闭合”的问题。
- 从 `challenged` 认识中寻找“争议边界”。
- 从 `new_question` 中识别重复风险和可计算性风险。
- 对 OpenAlex/Semantic Scholar 相似论文候选做 rerank，形成真正的新颖性风险报告。

验收标准：

1. 每个高优先级问题都有“为什么现在值得做”的变化依据。
2. 每个问题都有近 5 年相似工作风险标签。
3. 输出能被下游“纯计算可验证性判别 Agent”读取。

## 6. Phase 4：自动推送工程层

目标是让 Agent 从手动 CLI 变成周期性情报系统。

计划模块：

```text
watch_runner.py
digest_builder.py
notification_adapter.py
```

推荐节奏：

- 每日轻量运行：抓取新信源，生成 triage。
- 每周深度运行：更新 InsightLedger，生成周报。
- 每月评审运行：重新生成问题卡，更新新颖性风险和毕业价值排序。

推荐输出：

```text
outputs/intelligence/YYYY-MM-DD/
  new_sources.csv
  source_triage.md
  insight_delta_report.md
  novelty_risk_watch.md
  recommended_questions.md
```

验收标准：

1. 无需人工启动也能形成周期性输出。
2. 每次推送只强调变化，不重复灌输旧认识。
3. 能明确告诉用户：哪些认识增强了，哪些被挑战了，哪些问题值得进入下游 Agent。

## 8. Phase 2 第一版落地策略

认知收集层第一版采用“发现和分流优先，不自动下载封闭全文”的路线：

```text
SourceRegistry
  -> SourceHarvester
  -> SignalRanker
  -> new_sources.csv / source_triage.md
  -> local_pdf_inbox 或 licensed_tdm_api
```

默认实现：

- `source_registry.yaml`：登记 AI、AI4S、催化、ChemRxiv、arXiv 和本地 PDF inbox。
- `source_harvester.py`：接入 OpenAlex、Crossref、arXiv、ChemRxiv via Crossref prefix、Unpaywall 开放全文线索。
- `signal_ranker.py`：按相关性、年份、引用、开放可得性和信源等级打分。
- `source_intake.py`：把筛选后的候选源转成 workflow 可读取的抽象级 intake stubs，并输出全文获取队列。
- CLI：`python run_agent.py --config 06_config_real_ammonia_library.yaml --harvest --limit 20`。
- 端到端 CLI：`python run_agent.py --config 06_config_real_ammonia_library.yaml --harvest-workflow --limit 20`。

输出：

```text
outputs/intelligence/YYYY-MM-DD/
  new_sources.csv
  new_sources.jsonl
  source_triage.md
  source_harvest_summary.json
  intake/
  workflow/
```

该层只把候选分成：

- `oa_fulltext_ready`：开放全文可进入后续解析。
- `fulltext_queue`：高价值但需要人工/学校权限/TDM API 获取全文。
- `metadata_watch`：先观察，不进入正文证据抽取。
- `archive_low_signal`：低相关线索。

封闭出版社全文不走浏览器模拟作为主路径，避免工程维护成本和访问合规风险过早放大。

## 9. 安全与质量注意事项

- API key 应放在环境变量中，不应写入 YAML。
- 信源抓取必须遵守来源 API 和网站规则。
- LLM 输出只能作为候选认识和评审建议，不能直接作为论文结论。
- 所有高优先级问题仍需人工核验证据出处、DOI、年份、期刊和近年重复风险。
